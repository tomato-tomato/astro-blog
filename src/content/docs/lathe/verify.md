AI 写的教程最容易出问题的地方不是「讲得不对」，而是「照着敲跑不通」：代码块少半行、检查点的预期输出与实际不符、前置条件漏装一个工具，或者示例声明的版本和代码用到的特性根本不匹配。

验证就是把这件事交给 AI 真的跑一遍。

## 调用方式

```text
/lathe 验证 <slug>
/lathe verify <slug>
```

## 工作流程

**1. 读取元数据**——获取部分列表和所需工具。

**2. 版本一致性静态预检**——不运行代码，先比对三类版本信息：`metadata.json` 锁定的工具链版本、配置代码块声明的版本（如 `Cargo.toml` 的 `edition`）、示例代码实际使用特性所需的最低版本。发现冲突（例如 edition 2024 配 2021 语义的代码）直接进入修复流程，不等到运行才暴露。

**2b. 改动面静态预检**（v0.5.4 新增）——如果 `metadata.changed_interfaces` 非空，就对本次要执行的部分逐条核对：每个调用点在教程里是否有对应代码块、插在哪里、或者是否写明了「无需改动」。`runnable` 块里还留着旧签名、或者调用点没覆盖到，记为失败（改动面不完整）。被增量复用跳过的部分继承上次结果。**不做自动签名推断**——它只按清单核对，不猜。

**2c. 代码块结构预检**（v0.5.4 新增）——每个 `fragment` 必须写明所属文件与接缝，且同一部分里要有覆盖最终状态的 `runnable` 块或检查点；每个 `exercise` 必须有参考答案或检查方式。缺了就记为失败。这一步**只查结构**，不会去执行片段或练习。

**3. 标记为进行中**——写入 `verify-result.json`，状态设为 `verifying`。

**4. 准备验证工作区**——位于教程目录下的 `.lathe-verify/`（首次验证时创建，并在 `metadata.json` 中记录说明）。

- **全量执行**（从 `part-01` 开始）的触发条件：你明确要求全量；最后一个常规部分编号是 3 的倍数；`changed_interfaces` 与上次记录快照不一致；或者旧结果不可复用。
- 否则**增量复用**：上次已通过且对应部分未修改的直接跳过，从第一个需要执行的部分（失败 / 未跑 / 内容已变更 / 新增）继续，依赖与编译缓存直接复用。
- **级联失效**：从 `part-k` 重跑时，`part-k` 之后的常规部分默认不可复用，按顺序一起重跑。只有你明确说「只跑变更部分」时才会跳过，并标注风险。
- 针对特定仓库的教程（`repo` 非空）在工作区内克隆对应分支。

**5. 逐步执行**——按确定范围安装前置条件、创建文件、粘贴代码、运行检查点命令。执行范围由代码块类型决定（v0.5.4）：只跑 `runnable` 与 `expected_failure` 块和检查点；`fragment` / `exercise` / `text` / `output` 跳过、不单独粘贴。`expected_failure` 校验的是预期的非零退出或错误信息，**意外成功算失败**；`runnable` 块里出现 `...` 直接视为代码不完整。报错时先归因：版本冲突类错误进入修复流程，其他错误按失败处理。

**6. 更新横幅并记录结果**——先更新本次实际执行部分的**验证状态横幅**（通过就移除；失败或跳过写警告；没执行或复用跳过的不改），再写 `verify-result.json`（逐部分明细、`mode`、`changed_interfaces_snapshot`），并同步 `metadata.json` 的 `status`。顺序不能反：横幅是文件改动，会动 mtime，先写 `checked_at` 就会被下次列表误判成「内容已变更」。如果这次只改了横幅、正文没动，会刷新 `metadata.continuity.updated_at`，免得续写把它当成手工编辑；真改了正文则保留旧时间，让续写重建摘要。工作区保留，供下次增量验证使用。

## 版本冲突检测与修复

这是验证环节重点强化的能力，专门解决「教程示例声明的版本与文本介绍的特性相冲突，读者照着敲才发现报错」这类问题。

发现冲突时：

1. **展示冲突详情**：所在部分、代码块位置、冲突的版本与特性，并附证据（编译错误或官方文档链接）。
2. **提出两个修复方向**并给出建议：
   - **方案 A**：改代码 / 文本以对齐锁定版本（通常首选）
   - **方案 B**：调整版本声明，并同步更新 `metadata.json` 的 `tools`
3. **你确认后才修改**，改动最小化（只动冲突相关内容，不改 voice 和结构）；拒绝修复则保留原文，按失败记录。
4. **修复后重新执行该部分**，确认真正生效；修复内容记入 `verify-result.json` 对应部分的 `fixes` 数组。

## 安全护栏

- 所有命令只在验证工作区（`.lathe-verify/`）内执行，不碰你的项目和全局环境。
- 需要 `sudo`、全局安装、工作区外删除等敏感操作时会先向你确认；未确认则记为 `skipped`。
- 长时间运行的命令后台执行，验证后终止；单命令约 5 分钟无进展视为异常。
- 验证结束后工作区**静默保留**（不会询问是否清理）。它是隐藏目录，可以安全手动删除——下次验证会自动重建并全量执行。

## 三种验证结果

| 状态 | 含义 | 场景 |
| ---- | ---- | ---- |
| `verified` | 验证通过 | 所有检查点输出与教程声明一致（含经版本冲突修复后通过，修复记录在 `fixes`） |
| `skipped` | 跳过 | 缺少必需工具，或敏感操作未获确认 |
| `failed` | 验证失败 | 代码无法编译、输出不匹配、步骤矛盾（非版本冲突类，或你拒绝了修复） |

验证通过后 `metadata.json` 的 `status` 同步更新为 `verified`。逐部分明细写在 `verify-result.json`，失败部分会带 `failed_step` 与 `error` 字段（见[教程文件结构](/docs/lathe/file-structure/)）。逐部分状态比全局细，可以是 `passed` / `failed` / `skipped` / `not_run` / `not_applicable`；`failed_step` 只数 `runnable`、`expected_failure` 代码块和检查点命令，`fragment` / `exercise` / `text` / `output` 不占步骤号。

> 全局结果是 `skipped` 且没有逐部分明细时，各部分的横幅**保持不变**（不会替你写「已跳过」）。

## 注意事项

- 验证对教程部分**默认只读**。唯一例外是版本冲突修复，且必须先获你确认、改动最小化。
- `skipped` 不等于 `failed`——缺少工具是环境问题，不是教程问题。
- 验证前需要本地装好教程要求的工具链。
- 如果 `/lathe 列表` 显示某门课 *⚠️ 验证可能中断*（`verify-result.json` 停在 `verifying` 超过 6 小时），重新运行 `/lathe 验证 <slug>` 即可复位，增量复用会从断点继续。

## 验证失败之后

先看 `verify-result.json` 定位问题，改完 `part-NN.md` 再跑一次。更多排查思路见[常见问题](/docs/lathe/faq/)里的「验证失败了怎么办」。
